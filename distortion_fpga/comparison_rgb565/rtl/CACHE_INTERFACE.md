# 通用 RGB565 读取缓存

`src/rgb565_read_cache.v` 已通过独立和整帧 Verilog 仿真。它在原 engine 与通用块读取接口之间缓存源像素，不改动原插值数值、LUT 或 writer。当前仍是单请求、阻塞式基线，没有真实 DDR3 适配器、跨时钟域或每拍一像素的保证。

## 连接位置

摄像头写入并交出一块不再变化的源帧后，engine 的逻辑像素读口接缓存前端；缓存后端接板级块读取适配器；插值与目标帧回写继续走原路径。原九个算法 RTL 模块保持不变，新缓存是第十个独立模块。`sim/tb_package_cache.sv` 给出了完整仿真接线，不是 PDS 顶层。

所有端口属于同一个算法时钟。valid/ready 只在上升沿同时为 1 时传输；等待期间必须保持请求或响应不变。复位低有效、同步清状态，复位期间禁止所有缓存握手。实际跨时钟与 DDR 时钟必须由适配层处理。

## 前端像素接口

| 信号 | 含义 |
|---|---|
| req_valid req_ready req_addr | 接受一个逻辑像素地址，不是物理字节地址 |
| rsp_valid rsp_ready rsp_data | 返回一个规范化 RGB565，至少在请求接受后下一拍；支持等待 |
| invalidate_valid invalidate_ready | 清除所有行有效位和本帧计数，仅在空闲时接受 |
| busy | 当前请求尚未完成，包括响应被下游保持 |
| protocol_error | 后端协议错误，停止接受请求及返回像素，需缓存与后端联合复位 |
| request_count hit_count miss_count fill_beat_count | 本帧已接受请求、命中、未命中、接受补读 beat 的 32 bit 计数，复位或合法清缓存时归零 |

一次至多一个未完成前端请求。清缓存请求可以等待当前事务完成，但不能中断补读或被保持的前端响应；空闲时它优先于新像素请求。不要只打一拍 invalidate 然后忽略 ready。

源帧内容或基址改变前，必须先停止新请求、等待缓存空闲、完成 invalidate 握手，再使用新源帧。即使继续使用同一 DDR 基址，摄像头改写了内容也要清缓存。清缓存不能让正在被算法读取的帧安全地被摄像头覆盖；帧所有权仍由队友管理。

## 后端块读取接口

默认 `LINE_LOG2=4`，每块为 16 个连续逻辑像素、32 字节：

1. `line_req_valid && line_req_ready` 接受一块读取，`line_req_base_addr` 低 4 位为 0。地址仍按像素计数。
2. 最早下一拍开始响应，按 base、base+1、…、base+15 顺序返回 16 个规范化 RGB565。
3. 每个像素使用 `line_rsp_valid/ready/data` 握手。仅最后一个已传输像素的 `line_rsp_last=1`，其余必须为 0；等待时 data 与 last 保持。
4. 当前行完成后才返回前端请求的那个像素。不能将第一次返回的数据误当成整个块已经有效。

提前 last、最后缺少 last、或非补读期间出现响应都会进入错误状态；不返回伪造像素。复位缓存时必须同时取消/排空后端事务，旧响应没有事务 ID，不能混入新帧。

实际 DDR 可能一次返回 64/128 bit 或使用其他协议，适配器需将其转换为上述有序 16 bit beat。这个接口没有 AXI ID、物理突发长度、写通道或错误恢复重试。

紧密 RGB565 的物理字节地址由适配器计算 `source_base + 2*logical_address`。若有行 stride/padding，逻辑缓存块可能跨行，不能直接把它当作一个连续物理突发；后端必须按真实 stride 取正确像素并重组顺序。源帧不足整块时，要分配可安全补读的尾部 padding；测试后端对这些位置返回 0，禁止直接读取未分配的 DDR 地址。

## 容量与实现约定

默认 `SET_LOG2=9`，512 组，每组二路，精确二路 LRU；数据容量 `2 * 2**SET_LOG2 * 2**LINE_LOG2 * 2` = 32,768 字节。标签、有效位、LRU 与控制不在数据容量里，综合后的 BRAM/DSP/时序尚未测量。

命中时同步读取数据数组；未命中先使被替换行失效，全部正确 beat 收到后才提交新标签/有效位。复位不依赖清空像素 RAM，避免复用未完成的补读。32 bit 计数溢出按模 2³² 回绕，不能在无限长会话里把它当无限精度总数。

## 实际验证

两组独立测试：8 字节行/4 组，以及 32 字节行/8 组。每组 5,138 次人工读取，逐个核对返回像素，与软件 LRU 模型核对命中/未命中计数；覆盖同组冲突、最后偏移、随机请求等待/响应间隙、下游保持、换帧清缓存、补读中复位、响应保持时复位、last 错误、无请求响应及联合复位恢复。

默认 32 KiB 缓存、快速 mapper、16 bit 网格权重的两组完整帧：

| 人工参数 | 输出像素 | 无效像素 | 命中 | 未命中 | 接受补读像素 beat | 渲染仿真周期 |
|---|---:|---:|---:|---:|---:|---:|
| 30° 保持中心裁剪 | 921,600 | 0 | 3,665,207 | 21,193 | 339,088 | 24,095,481 |
| 20° 保留画布 | 921,600 | 97,364 | 3,223,833 | 73,111 | 1,169,776 | 25,121,150 |

两帧全部 RGB565 像素及输出地址与原整数标准一致，计数与 `memory_profile.py` 的假设模型完全一致。报告在对应 `out/package-…-fast-cachel4s9/result.json`，包含当前 RTL/测试平台校验码。

另有 35×23 恒等图，源帧 805 个像素，不足整行的末块包含 11 个 padding 像素。两套网格权重 × 两种 mapper，共四帧逐像素通过，均为 3,220 个逻辑请求、3,169 命中、51 次未命中、816 个补读 beat。证明末块和短网格单元已覆盖，不是仅测尺寸整除的 720P。

缓存与无缓存测试使用不同的后端模型，**不能把周期差值当作实板缓存加速比**。目前仍需物理 DDR 适配、多请求/处理流水化、真实时序与端到端吞吐测量。

## 复现

项目根目录：

```powershell
.\rtl\run.ps1 test
.\rtl\run.ps1 tools/small_cache_demo.py
.\rtl\run.ps1 tools/run_package_sim.py --package out/demo720p --fast-map --cache
.\rtl\run.ps1 tools/run_package_sim.py --package out/center30 --fast-map --cache
```

完整帧需先按 README 生成测试包；`--cache-line-log2`、`--cache-set-log2` 可调整容量和块大小。软件重新计算该参数下的标准计数，不能用另一种容量的报告做比较。
